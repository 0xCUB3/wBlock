# HaGeZi's lists in wBlock

In short, HaGeZi's lists are good lists made mainly for DNS blocking. In Safari they mostly cost rule space that browser-focused lists put to better use. HaGeZi recommends content filter lists for mobile ad blockers and DNS lists at the DNS level, and wBlock follows the same split. HaGeZi Multi Pro Mini stays available in wBlock for anyone who wants it, but it isn't one of the recommended lists.

HaGeZi publishes these lists in the [dns-blocklists](https://github.com/hagezi/dns-blocklists) repository. They come in formats for DNS servers such as Pi-hole and AdGuard Home and in an AdBlock format that browser blockers can also read. The repository describes Pro Mini as "a size-optimized version made for DNS or browser blockers," and HaGeZi has [recommended Pro Mini](https://github.com/hagezi/dns-blocklists/issues/10246#issuecomment-4490774902) as the starting point for browser ad blockers. So the warning is about how the lists fit Safari and not about their quality.

Every rule in these lists blocks a whole domain. The Pro Mini file wBlock downloads had 93,657 rules on November 3, 2026, and every one has the form `||example.com^`. There is no element hiding, no scriptlets, no path rules and no exceptions. That is by design. HaGeZi's [FAQ](https://github.com/hagezi/dns-blocklists/blob/main/FAQ.md) explains that rules depending on "URLs, paths, page context, exceptions, or ambiguous pattern logic are not blindly converted into DNS entries."

Safari compiles each content blocker from at most 150,000 rules ([WebKit source](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/contentextensions/ContentExtensionParser.cpp)). Pro Mini alone fills about 62% of one of wBlock's five blockers. The full Pro list has 211,778 entries and would not fit in one at all.

About 31% of Pro Mini's domains are already blocked by wBlock's recommended lists. Those lists can also block a single ad path on a domain a site needs and hide the gap an ad leaves behind. A domain-only rule can do neither. When a site depends on something served from a listed domain, that part of the site stops working and the list has no exception to fix it.

On iOS, Safari also has to load these rules within the memory iOS gives a content blocker. Asked about using these lists in wBlock, HaGeZi [wrote](https://github.com/hagezi/dns-blocklists/issues/10246#issuecomment-4491094864) "For mobile ad blockers, I would only use content filter lists, not DNS lists. Instead, use an upstream DNS with the appropriate lists." HaGeZi's own iOS devices run uBlock Origin Lite in Safari with HaGeZi's DNS servers upstream. uBlock Origin doesn't include any HaGeZi list in its built-in catalog either.

DNS blocking is where these lists do the most good. It covers every app on the device and not just Safari, and it costs no Safari rule capacity. To use HaGeZi's lists that way, keep wBlock on its recommended lists and set your device's DNS to a service that offers them. HaGeZi keeps a [list of DNS services](https://github.com/hagezi/dns-blocklists#dnsservices) that do.
